# Ввод в эксплуатацию: от стенда к пяти площадкам

Стенд из двух серверов прошёл приёмку. Дальше — реальные площадки. Здесь
собрано то, что на стенде не проявляется, но обязательно вылезет в бою.

## Шаг 0. Нумерация — до всего остального

По результатам аудита существующей инфраструктуры (11 АТС, 6 регионов,
1216 абонентов) обнаружены **конфликты кодов площадок**: один и тот же
внутренний номер существует на разных АТС.

Пока это не решено, объединять нечего: единый план нумерации — предпосылка
кластера, а не его следствие. Два абонента с номером 564 в одной таблице
`ps_endpoints` — это не «разберёмся потом», это невозможность завести
вторую строку с тем же первичным ключом.

Проверяется автоматически:

```bash
./scripts/check-numbering.py \
    --dump rostov=pbx1-10.1.10.111/sql/asterisk-db.sql \
    --dump voronezh=voronezh-dump.sql \
    --csv slavyansk=slavyansk-ext.csv \
    --plan 5
```

Источники можно смешивать: дампы FreePBX (`--dump`), выгрузки в CSV
(`--csv`) и подключение к работающей АТС (`--live user:pass@host/db`).

Скрипт покажет занятые диапазоны по каждой площадке, номера, встречающиеся
более чем на одной АТС, и — при указании `--plan` — крупные свободные
блоки, куда переносить конфликтующих. Возвращает ненулевой код, если
конфликты найдены, так что его можно поставить в конвейер проверок.

> **Проверка на реальных данных Ростова** показала ещё одну особенность:
> план нумерации смешанной длины — 3-значные (201–481), 4-значные и
> 5-значные (10888–10999) одновременно. Это не конфликт сам по себе, но
> при объединении такие планы пересекаются охотнее, и кластерный диалплан
> обязан покрывать все длины. В шаблонах покрыты 3, 4 и 5 знаков; появится
> 6-значный план — добавьте шаблон по образцу в
> `config/asterisk/extensions_master_hook.conf.tpl`.

Дальше: утвердить схему (код площадки + номер единой длины), провести
перенумерацию конфликтующих площадок **до** миграции — со своим планом
уведомления пользователей и переходным периодом, когда старый номер
переадресуется на новый.

Только после этого — шаг 1.

## Шаг 1. Сеть между площадками

Кластер предполагает, что площадки видят друг друга по приватным адресам.

Требования:

| Параметр | Значение | Почему |
|---|---|---|
| RTT между узлами | < 20 мс хорошо, < 50 мс терпимо | Galera подтверждает запись синхронно |
| Потери | < 0.1% | потери вызывают ложные разрывы кластера |
| Полоса | от 10 Мбит/с + запас на RTP | SST копирует всю базу целиком |
| Каналы | site-to-site VPN или L2 | межузловые транки ходят без шифрования SIP |

Проверять до установки:

```bash
./scripts/preflight.sh --node-ip=<этот> --peers=<все через запятую>
```

Если RTT до какой-то площадки стабильно выше 50 мс — эту площадку в Galera
включать не надо. Варианты для неё в разделе «Площадка на плохом канале».

## Шаг 2. Порядок ввода площадок

По одной. Не все сразу.

```bash
# 1. Preflight на новой площадке
./scripts/preflight.sh --node-ip=10.4.3.6 --peers=<полный список>

# 2. Установка
./scripts/clone-node.sh \
  --node-name=voronezh --node-ip=10.4.3.6 \
  --master-ip=10.10.10.11 --master-node-name=rostov \
  --peers=<полный список, включая новую> \
  --cluster-name=asterisk_prod --asterisk-major=21 \
  --sst-pass='...' --rt-pass='...'

# 3. Транки — на ВСЕХ узлах с обновлённой картой
./scripts/make-node-trunks.sh --peers-map=rostov=10.10.10.11,voronezh=10.4.3.6,...

# 4. Конфигурация с мастера
asterisk-cluster-sync --apply
asterisk-cluster-push-dialplan --nodes=voronezh=10.4.3.6,...

# 5. Проверка
asterisk-cluster-health
```

### Про `--peers`: список должен быть полным на всех узлах

Самая частая ошибка при тиражировании. `wsrep_cluster_address` на каждом
узле обязан содержать **все** узлы кластера, а не только мастер и себя.

Если этого не сделать, всё будет работать ровно до первого одновременного
рестарта: узлы не найдут друг друга, потому что знают только про мастер,
который тоже перезагружается.

Поэтому при добавлении пятой площадки нужно обновить конфигурацию **всех
четырёх** предыдущих. Для этого есть отдельный скрипт — он проверяет
кворум и не даёт уронить кластер неосторожным перезапуском:

```bash
# на КАЖДОМ уже работающем узле, по одному
./scripts/update-peers.sh --peers=<НОВЫЙ полный список> --restart
```

Что он делает:

- проверяет, что все адреса корректны и текущий узел есть в списке;
- обновляет `60-galera.cnf` и `PEERS` в `cluster.env`, чтобы они не
  разъехались;
- **отказывается перезапускаться**, если после ухода этого узла оставшиеся
  потеряют кворум (обойти можно `--force`, но это осознанная остановка);
- дожидается состояния `Synced` до 300 секунд и перезагружает ODBC в
  Asterisk, который мог потерять realtime на время рестарта.

Без `--restart` скрипт только правит конфигурацию: новый список вступит в
силу при следующем плановом перезапуске. Это безопасно отложить —
работающий кластер продолжает использовать уже установленные соединения.

Обходите узлы **строго по одному**, дожидаясь завершения на предыдущем.

## Шаг 3. Транки провайдеров

На стенде все внешние транки живут на мастере, площадки отдают исходящие
туда. В бою так делать не стоит: падение мастера оставляет все площадки без
внешней связи, хотя их собственные каналы живы.

Правильная схема — **локальные транки на каждой площадке**. Операторы
допускают до 10 точек подключения к виртуальной АТС, поэтому каждая
площадка регистрируется сама:

```bash
./scripts/setup-local-trunk.sh \
  --trunk-name=mango-voronezh --host=vpbx.mango-office.ru \
  --user=<пользователь ВАТС этой площадки> --pass='...' \
  --did=4732XXXXXX
```

Исходящие идут через свой транк, при `CHANUNAVAIL` или `CONGESTION` —
через мастер. Входящие приходят прямо на площадку.

> **Главное правило: у каждой площадки свой пользователь ВАТС.** Общий
> аккаунт на всех даёт рабочие исходящие, но ломает входящие — оператор не
> знает, какой из зарегистрированных точек адресован вызов.

По этой же причине `ps_registrations` **исключена из realtime**: таблица
общая на кластер и не различает узлы, поэтому вынесенный туда транк
заставил бы регистрироваться все площадки сразу одним аккаунтом.
`sync-config.py` не переносит `pjsip.registration.conf`.

Подробно: [11-local-trunks.md](11-local-trunks.md).

## Шаг 4. Кворум на пяти площадках

Пять узлов дают честный кворум без арбитра: кластер переживает потерю двух
узлов. Отдельный `garbd` не нужен.

Но стоит понимать географию отказов. Если три площадки сидят за одним
каналом, обрыв этого канала оставляет 3 против 2 — меньшинство из двух
площадок встанет. Если такая топология неизбежна, поставьте арбитра на
независимой площадке, чтобы сместить баланс.

## Шаг 5. Мастер как единственная точка управления

При падении мастера звонки идут, а управление недоступно: ни завести номер,
ни поменять IVR, ни пересобрать конфиги телефонов.

**Тёплый резерв** — реализован скриптом. Отдельный узел входит в Galera и
потому непрерывно держит актуальную базу, но Asterisk и веб-интерфейс на
нём остановлены: телефоны туда не регистрируются, вызовы не обслуживаются.

```bash
# Подготовка (однократно). FreePBX и Asterisk той же версии должны быть
# уже установлены на этом узле.
./scripts/setup-standby-master.sh --prepare \
    --node-name=rostov-standby --node-ip=10.1.10.112 \
    --master-ip=10.1.10.111 --master-node-name=rostov \
    --peers=10.1.10.111,10.1.10.112,10.4.3.6 \
    --sst-pass='...' --rt-pass='...'

# Регулярная проверка готовности
./scripts/setup-standby-master.sh --status

# Переключение при аварии
./scripts/setup-standby-master.sh --promote

# Возврат в резерв, когда основной вернулся
./scripts/setup-standby-master.sh --demote
```

Восстанавливать при переключении нечего: номера, диалплан, настройки
модулей и данные Endpoint Manager уже приехали репликацией. Время
переключения — минуты, цена — одна простаивающая VM.

`--promote` отказывается работать, если узел не в состоянии `Synced`, и
предупреждает, если основной мастер всё ещё отвечает на 5060. Два
одновременно работающих мастера — это два веб-интерфейса, пишущих в одну
базу, и телефоны, разошедшиеся между ними.

Чего скрипт **не** делает автоматически: не переносит IP и не переключает
телефоны — это зависит от вашей сети. Варианты: перенести адрес основного
мастера на резервный либо обновить резервный сервер в шаблоне Endpoint
Manager и пересобрать конфиги. Скрипт печатает этот список после
переключения.

Альтернатива для случаев, когда нужны секунды, а не минуты, — **Kamailio
перед кластером**, см. ниже. Бэкап мастера обязателен в любом варианте,
см. [05-operations.md](05-operations.md).

## Площадка на плохом канале

Если до площадки RTT больше 50 мс или канал нестабилен, включать её в Galera
вредно: она будет тормозить запись во всём кластере через flow control.

Варианты:

- **Асинхронная реплика.** Площадка получает копию базы обычной
  MySQL-репликацией с одного из узлов Galera и работает на чтение. Номера
  видит, регистрации держит локально. Цена: `ps_contacts` этой площадки не
  видны остальным, межузловая маршрутизация к ней работать не будет —
  вызовы придётся направлять статически.
- **Автономная АТС с транком.** Площадка живёт сама по себе, связана с
  кластером обычным SIP-транком и статическим маршрутом по диапазону
  номеров. Проще всего и надёжнее всего при плохой связности.

## Когда нужен Kamailio

Схема с dual-registration даёт переключение за 10–60 секунд. Этого хватает
для офисной телефонии. Kamailio перед Asterisk имеет смысл, если:

- требуется переключение за секунды (диспетчерская, аварийные службы);
- телефонов больше нескольких тысяч и запись в `ps_contacts` становится
  заметной нагрузкой на репликацию;
- нужен единый SIP-адрес площадки с балансировкой между несколькими
  Asterisk.

Kamailio берёт на себя регистрацию (usrloc в общей БД) и раскидывает вызовы
модулем `dispatcher`, Asterisk остаётся медиа-сервером и логикой. Это
существенно более сложная система: отдельный слой конфигурации, свой
мониторинг, своя отладка. Для пяти площадок с обычной офисной нагрузкой —
избыточно.

## Контрольный список перед боем

Проверяемое автоматически:

```bash
./scripts/check-numbering.py --dump ...        # конфликтов нет -> код 0
./scripts/preflight.sh --node-ip=... --peers=...   # на каждом узле
./scripts/harden.sh                            # без пунктов «требует вмешательства»
asterisk-cluster-health                        # на каждом узле
./scripts/setup-standby-master.sh --status     # на резервном мастере
./tests/run-all.sh                             # если правили комплект
```

Остальное — глазами:

- [ ] Нумерация приведена к единому плану, конфликтов нет
- [ ] `preflight.sh` на всех узлах без `FAIL`
- [ ] RTT между всеми парами площадок измерен и записан
- [ ] `--peers` полный и одинаковый на всех узлах
- [ ] Пароли `ChangeMe_*` нигде не остались; секреты — в менеджере секретов
- [ ] Запасное правило ufw `allow 22/tcp` сужено до админской подсети
- [ ] Бэкап базы настроен и **проверен восстановлением**
- [ ] `asterisk-cluster-health` зелёный на всех узлах
- [ ] Мониторинг собирает метрики со всех узлов
- [ ] Написана и опробована процедура восстановления кворума
- [ ] Локальные транки на площадках работают без мастера
- [ ] Проверено: отключение мастера не роняет звонки между площадками
- [ ] Резервный мастер подготовлен, `--status` показывает готовность
- [ ] Переключение на резерв **опробовано на стенде**, а не только описано
- [ ] Обновление списка узлов проверено: `update-peers.sh` отказывается
      перезапускаться при потере кворума
