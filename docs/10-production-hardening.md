# Доведение до продакшена: аудит и усиление

Разбор конфигурации АТС 10.1.10.111 (FreePBX 16.0.47, Asterisk 18.26.1,
444 добавочных, 284 телефона в EPM) и что нужно исправить до вывода
кластера в эксплуатацию.

Всё перечисленное найдено в самих конфигах, а не выведено из общих
соображений. Применяется скриптом:

```bash
./scripts/harden.sh              # план
./scripts/harden.sh --apply      # применить безопасную часть
```

## Что нашлось

### 🔴 Журнала безопасности нет, а порт 5060 смотрит наружу

В транспорте задан публичный адрес:

```
external_media_address=212.46.215.186
external_signaling_address=212.46.215.186
bind=0.0.0.0:5060
```

При этом в `logger_logfiles_additional.conf` только два канала:

```
console => warning
full => error,notice,verbose,warning
```

Канала `security` нет. Значит `/var/log/asterisk/security` не пишется,
fail2ban читать нечего, и перебор добавочных идёт незамеченным. Сканеры SIP
находят открытый 5060 за часы, а 444 добавочных — это 444 попытки подобрать
пароль и звонить за ваш счёт.

Скрипт добавляет канал `security` в `logger_logfiles_custom.conf` (этот файл
FreePBX не перезаписывает) и ставит fail2ban с фильтром `asterisk`:
5 неудач за 10 минут → бан на час, рецидив → на сутки.

Это защита от перебора, а не замена сильным паролям. После утечки дампа
пароли всё равно подлежат ротации.

### 🟠 anonymous в начале порядка идентификации

```
endpoint_identifier_order=ip,username,anonymous,header,auth_username
```

`anonymous` стоит третьим — раньше, чем `header` и `auth_username`. Вызов,
не опознанный по IP и username, будет принят как анонимный, хотя мог бы
опозняться дальше по цепочке.

Правильный порядок: `username,auth_username,ip,header`, а `anonymous` —
последним либо вовсе убрать. Меняется в интерфейсе: **Settings → Asterisk
SIP Settings → PJSIP → Endpoint Identifier Order**. Скрипт это только
диагностирует: параметр генерируется FreePBX в `pjsip.conf`, и правка файла
будет затёрта при следующем Apply Config.

Смягчающее обстоятельство: `allowguest=no` в настройках chan_sip, то есть
гостевые вызовы запрещены. Но порядок всё равно стоит привести в норму.

### 🟠 ulaw первым кодеком

```
allow=ulaw,alaw,gsm,g726,g722,h264,mpeg4,vp8
```

Российские операторы работают на **alaw**. С ulaw первым каждый внешний
вызов идёт через транскодирование: лишняя нагрузка на процессор и потеря
качества на ровном месте. На 444 абонентах это заметно.

Меняется в **Settings → Asterisk SIP Settings → Codecs**: перетащить alaw
наверх, Apply Config. Заодно стоит отключить `h264, mpeg4, vp8`, если
видеотелефонов нет — они только раздувают SDP.

### 🟡 AMI слушает все интерфейсы

```
bindaddr = 0.0.0.0
```

Пользователи ограничены `permit=127.0.0.1`, поэтому подключиться снаружи
нельзя. Но открытый порт 5038 отвечает баннером с версией Asterisk — это
подсказка для атакующего и лишняя цель для сканера. Скрипт меняет на
`127.0.0.1`.

Проверьте после применения, что панель `cxpanel` продолжает работать: она
ходит в AMI и тоже с localhost, так что не должна пострадать.

## Что проверено и менять не нужно

Чтобы не тратить время на ложные тревоги — эти вещи в вашей конфигурации
уже в порядке:

| Параметр | Значение | Комментарий |
|---|---|---|
| `direct_media` | `no` | правильно для NAT и записи разговоров |
| `rtp_symmetric`, `force_rport`, `rewrite_contact` | `yes` | корректная работа за NAT |
| `rtp_timeout` | `30` | зависшие каналы освобождаются |
| `strictrtp` | `yes` | защита от подмены RTP-потока |
| RTP-диапазон | `10000–20000` | достаточно на 444 абонента |
| `max_contacts` / `remove_existing` | `1` / `yes` | совместимо с кластером, см. ниже |
| `allowguest` | `no` | гостевые вызовы запрещены |
| AMI-пользователи | `deny=0.0.0.0/0, permit=127.0.0.1` | доступ только локальный |
| `tos_audio=ef`, `cos_audio=5` | | приоритизация голоса настроена |

### Про `max_contacts=1` и кластер

Это сочетание (`max_contacts=1` + `remove_existing=yes`) означает: у абонента
всегда ровно одна активная регистрация. При переключении на мастер запись
площадки удаляется, при возврате — наоборот.

Для маршрутизации это даже удобно: `ps_contacts` всегда содержит один
однозначный ответ на вопрос «где абонент». Есть короткое окно, когда запись
указывает на уже недоступный узел — но диалплан это обрабатывает: при
`CHANUNAVAIL` или `CONGESTION` на межузловом плече вызов повторяется
локально (см. `config/asterisk/extensions_cluster.conf.tpl`).

Менять на `max_contacts=2` не нужно.

## Порядок работ до продакшена

Последовательность важна: сначала безопасность и ротация, потом кластер.

### 1. Закрыть периметр

```bash
./scripts/harden.sh --apply
```

Затем вручную в интерфейсе: порядок идентификации и кодеки (см. выше).

### 2. Сменить пароли

Обязательно после публикации дампа:

- **SIP-пароли абонентов** — FreePBX, модуль Bulk Handler: выгрузить
  добавочные в CSV, сгенерировать новые пароли, загрузить обратно.
  Телефоны получат их автоматически через EPM при следующем провижининге.
- **Учётки транков** — у Ростелекома и Манго, через личный кабинет.
- **AMI** (`manager.conf`, `manager_additional.conf` для cxpanel).
- **`freepbxuser`** — через `fwconsole` или вручную в
  `res_odbc_additional.conf` и `/etc/freepbx.conf` одновременно.

После смены SIP-паролей — `fwconsole endpoint rebuildall`, чтобы телефоны
забрали новые.

### 3. Проверить восстановление из бэкапа

```bash
fwconsole backup --backup=1
```

Разверните копию на отдельной VM и убедитесь, что она поднимается.
Непроверенный бэкап бэкапом не является — а следующий шаг перезапускает БД.

### 4. Принять АТС в кластер

```bash
./scripts/adopt-master.sh --node-name=rostov --node-ip=10.1.10.111 \
    --peers=10.1.10.111,10.4.3.6 --cluster-name=asterisk_prod
```

Требуется окно: MariaDB перезапускается, новые вызовы не устанавливаются
около минуты. Активные разговоры не рвутся.

### 5. Развернуть первую площадку

Только одну, и обкатать на ней неделю, прежде чем тиражировать.

```bash
./scripts/clone-node.sh --node-name=voronezh --node-ip=10.4.3.6 \
    --master-ip=10.1.10.111 --master-node-name=rostov \
    --peers=10.1.10.111,10.4.3.6 --cluster-name=asterisk_prod \
    --asterisk-major=18 --sst-pass='...' --rt-pass='...'
./scripts/make-node-trunks.sh --peers-map=rostov=10.1.10.111,voronezh=10.4.3.6
```

### 6. Включить failover телефонов

Правка шаблона EPM плюс расстановка площадок —
[09-epm-integration.md](09-epm-integration.md).

Начните с одного телефона: заведите его в `sites.conf`, пересоберите
конфиг, проверьте, что он зарегистрировался на площадке и переключается на
мастер при её остановке. Только потом — на всех.

## Приёмка

Кластер считается готовым к эксплуатации, когда проходит всё:

**Безопасность**
- [ ] `/var/log/asterisk/security` наполняется
- [ ] `fail2ban-client status asterisk` показывает активное правило
- [ ] тестовый перебор с внешнего адреса приводит к бану
- [ ] пароли сменены: абоненты, транки, AMI, БД
- [ ] `ss -tulnp | grep -vE '127.0.0.1|::1'` — наружу смотрит только то, что должно

**База**
- [ ] `wsrep_cluster_size` одинаков на всех узлах
- [ ] `wsrep_local_state_comment = Synced` везде
- [ ] `asterisk-cluster-health` без замечаний на всех узлах
- [ ] бэкап снимается по расписанию и **проверен восстановлением**

**Телефония**
- [ ] число добавочных после перехода совпадает с исходным
- [ ] `SELECT reg_server, COUNT(*) FROM ps_contacts GROUP BY reg_server` —
      телефоны распределены по площадкам, пустых `reg_server` нет
- [ ] звонок внутри площадки проходит
- [ ] звонок между площадками проходит в обе стороны
- [ ] внешние вызовы через транки работают
- [ ] `*777` называет обслуживающий узел

**Отказоустойчивость**
- [ ] остановка Asterisk на площадке → телефоны уходят на мастер за 10–60 с
- [ ] звонки на них в это время проходят
- [ ] возврат площадки → телефоны возвращаются
- [ ] остановка мастера → площадки продолжают обслуживать внутренние вызовы
- [ ] обрыв связи между площадками → кворум сохраняется, меньшинство
      восстанавливается через `galera-recover.sh`

**Эксплуатация**
- [ ] `asterisk-cluster-sync --apply` после Apply Config отрабатывает
- [ ] `asterisk-cluster-push-dialplan` доставляет диалплан на площадки
- [ ] метрики уходят в мониторинг, алерты настроены
- [ ] процедура восстановления кворума опробована на стенде, а не прочитана

## Что остаётся нерешённым

Честно, чтобы не было сюрпризов:

- **Мастер — единственная точка управления.** При его отказе звонки идут,
  но завести номер или поменять IVR негде. Варианты усиления описаны в
  [04-production-rollout.md](04-production-rollout.md), но не автоматизированы.
- **Транки живут на мастере.** Пока не сделаны локальные транки на
  площадках, отказ мастера оставляет всех без внешней связи. Это следующий
  по важности шаг после запуска кластера.
- **TLS/SRTP не настроен.** В `keys/` только `.csr`. Для внутренней сети
  приемлемо, для абонентов через интернет — нет.
- **Репликация Galera идёт открытым текстом** и рассчитывает на доверенную
  сеть между площадками. Нужен VPN.
