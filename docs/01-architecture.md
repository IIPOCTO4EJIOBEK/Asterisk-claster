# Архитектура кластера

## Задача

Пять площадок. Абоненты регистрируются на своей площадке, но если она
недоступна — переключаются на мастер и продолжают работать. Номера, транки и
диалплан едины для всех: изменение в одном месте видно везде.

## Три независимых слоя

Отказоустойчивость строится не одним механизмом, а тремя — у каждого свой
режим отказа и своё время восстановления.

```
┌──────────────────────────────────────────────────────────────────┐
│ Слой 3. Регистрация телефонов                                    │
│   primary = своя площадка, backup = мастер                       │
│   переключение: 10-60 с (таймер телефона)                        │
├──────────────────────────────────────────────────────────────────┤
│ Слой 2. Asterisk                                                 │
│   мастер: FreePBX — источник правды по номерам и диалплану       │
│   площадки: headless Asterisk на realtime                        │
│   маршрутизация между узлами по ps_contacts.reg_server           │
├──────────────────────────────────────────────────────────────────┤
│ Слой 1. MariaDB Galera — единый источник правды                  │
│   multi-master, синхронная репликация                            │
│   ps_endpoints / ps_aors / ps_auths / ps_contacts                │
└──────────────────────────────────────────────────────────────────┘
```

## Слой 1: база данных

MariaDB Galera на всех площадках, multi-master. Каждый Asterisk работает со
своим локальным узлом БД — чтения быстрые, а записи синхронно
подтверждаются кластером.

Почему Galera, а не «мастер + асинхронные реплики»: при отказе мастера
асинхронная схема требует промоушена реплики (10–30 с недоступности записи и
риск потерять последние транзакции). В Galera любой узел принимает запись
всегда, пока он в кворуме.

Цена: запись подтверждается всеми узлами, поэтому задержка между площадками
напрямую входит в время транзакции. При RTT выше 20 мс это уже заметно, выше
50 мс — болезненно. `scripts/preflight.sh` измеряет RTT и предупреждает.

**Кворум.** Живая часть кластера должна содержать больше половины голосов.
На пяти площадках это работает само. На двух узлах (лабораторный стенд)
любой обрыв связи оставляет обе стороны в меньшинстве — нужен третий голос,
арбитр `garbd`, и он обязан стоять **на отдельном хосте**: арбитр на мастере
исчезает вместе с мастером и кворума не спасает.

## Слой 2: Asterisk

**Мастер** работает под FreePBX. Это единственное место, где заводят номера,
IVR, очереди и время работы. GUI нужен людям, а не серверам, поэтому он один.

**Площадки** — headless Asterisk без GUI. Всю конфигурацию они берут из двух
источников:

| Что | Как попадает на площадку | Чем |
|---|---|---|
| Добавочные, AOR, учётки, транки | realtime-таблицы `ps_*` в общей БД | `scripts/sync-config.py` |
| Диалплан, IVR, очереди, MoH | rsync файлов с мастера | `scripts/push-dialplan.sh` |
| Регистрации телефонов | общая таблица `ps_contacts` | сам Asterisk |

Разделение не случайно. Номера — это строки в таблицах, они прекрасно живут
в realtime. Диалплан FreePBX — это сгенерированные файлы с макросами и
Gosub'ами, загонять их в realtime-таблицу `extensions` бессмысленно и хрупко.

> **Важно.** FreePBX **не** заполняет таблицы `ps_*` сам. Он хранит
> добавочные в своих таблицах и по Apply Config рендерит из них статические
> файлы `/etc/asterisk/pjsip.*.conf`. Поэтому нужен `sync-config.py`: он
> читает то, что FreePBX уже отрендерил, и переносит в realtime-схему.
> Запускать его надо после каждого Apply Config.

## Слой 3: регистрация и failover

Каждому телефону прописываются два регистратора: primary — своя площадка,
backup — мастер. Провижининг выдаёт оба сразу, при первом включении
(см. [03-provisioning.md](03-provisioning.md)).

Переключение занимает от 10 до 60 секунд — это таймер самого телефона.
Если нужны секунды, перед Asterisk ставится слой Kamailio; для пяти площадок
с обычной офисной телефонией это избыточно (см.
[04-production-rollout.md](04-production-rollout.md), раздел «Когда нужен
Kamailio»).

## Как звонок находит абонента на другой площадке

Это то, ради чего регистрации вынесены в общую БД.

1. У каждого узла в `asterisk.conf` задан `systemname` — имя площадки.
2. Когда телефон регистрируется, `res_pjsip` пишет строку в `ps_contacts` и
   проставляет в поле `reg_server` этот самый `systemname`.
3. Таблица общая, значит **любой** узел знает, где физически находится любой
   абонент.
4. Диалплан спрашивает об этом через `func_odbc` (`ODBC_CONTACT_NODE`) и либо
   звонит локально, либо ведёт вызов через межузловой транк `node-<площадка>`.

```
Абонент 564 звонит на 720.

  [Воронеж]  SELECT reg_server FROM ps_contacts WHERE endpoint='720'
             -> 'rostov'
  [Воронеж]  Dial(PJSIP/720@node-rostov)
                     │
                     ▼
  [Ростов]   context=from-cluster -> Dial(PJSIP/720) -> телефон
```

Если транк до площадки мёртв, вызов возвращается к локальной обработке:
телефон мог уже перерегистрироваться сюда, а старая запись в `ps_contacts`
ещё не истекла.

Транки генерирует `scripts/make-node-trunks.sh` — полная сетка «каждый с
каждым», аутентификация по IP поверх доверенной межплощадочной сети.

## Что где живёт

| Компонент | Мастер | Площадка |
|---|---|---|
| MariaDB Galera | да | да |
| FreePBX GUI | да | нет |
| Asterisk | да | да (headless) |
| Транки провайдеров | да | опционально (см. rollout) |
| Сервер провижининга | да | нет |
| `systemname` | имя мастера | имя площадки |
| Источник номеров | свои таблицы FreePBX | realtime `ps_*` |
| Источник диалплана | FreePBX | rsync из `from-master/` |

## Режимы отказа

| Что отказало | Что происходит | Восстановление |
|---|---|---|
| Asterisk на площадке | телефоны уходят на мастер | 10–60 с, автоматически |
| Площадка целиком | то же + её транки недоступны | автоматически |
| Мастер | площадки работают, GUI недоступен, новые номера не завести | ручное, см. operations |
| Связь между площадками | меньшинство уходит в non-Primary | `galera-recover.sh` |
| Узел БД на площадке | Asterisk теряет realtime | рестарт узла, SST |

Отдельно стоит понимать: **мастер — единственная точка отказа для
управления**. Звонки при его падении идут, но завести новый номер или
поменять IVR будет негде, пока он не вернётся. Варианты усиления — в
[04-production-rollout.md](04-production-rollout.md).
